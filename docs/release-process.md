# Release Process

This document describes how maintainers publish a new release of the
`libnss-docker-ng` Debian package.

---

## Overview

The Git tag is the explicit human release approval boundary.  Once a valid
release tag is pushed, the release workflow runs automatically:

1. **Version consistency check** — validates the tag, `debian/changelog`, and
   `Cargo.toml` are mutually consistent.
2. **Package build and validation** — runs the same CI pipeline that validates
   every push to `main` (Debian Trixie build, lintian, install/removal lifecycle
   test, Docker NSS smoke test).
3. **GitHub Release publication** — only if all checks pass: collects build
   artifacts, generates SHA-256 checksums, and publishes a GitHub Release.

A release is **never published** if any version check or package validation
fails.

---

## Version semantics

| Item | Example |
|------|---------|
| Upstream version | `1.2.1` |
| Debian package version | `1.2.1-1` |
| Release tag | `debian/1.2.1-1` |

The Debian **revision** (the `-N` suffix) increments independently for
packaging-only changes.  A future packaging fix is released as:

| Item | Example |
|------|---------|
| Upstream version | `1.2.1` (unchanged) |
| Debian package version | `1.2.1-2` |
| Release tag | `debian/1.2.1-2` |

### Rules

- The tag format is `debian/<debian-package-version>`.
- The version in the tag must exactly match the first entry in
  `debian/changelog`.
- The upstream portion of the Debian version (everything before the last
  `-<revision>` suffix) must match the `version` field in `Cargo.toml`.
- Tags of any other form are rejected by the workflow.

---

## Prerequisites for a new release

Before pushing a release tag:

1. **The tagged commit is on `main` and has been reviewed.**  The workflow
   does not build from unreviewed branches or PRs.
2. **`debian/changelog` has been updated** with a new entry for the version
   being released.
3. **`Cargo.toml` version** matches the upstream portion of the Debian
   package version.
4. **All CI checks pass** on the commit being tagged.

---

## Normal release sequence

### 1. Prepare the packaging commit

Ensure `debian/changelog` leads with the new version:

```
nss-docker-ng (1.2.1-1) unstable; urgency=low

  * Initial Debian package.
  * Closes: #1119131

 -- Your Name <you@example.com>  Mon, 01 Sep 2026 12:00:00 +0000
```

Commit and push to `main`.  Confirm CI is green before tagging.

### 2. Create the release tag

```sh
# Lightweight tag (minimum requirement):
git tag debian/1.2.1-1

# Signed tag (recommended when a GPG key is available):
git tag -s debian/1.2.1-1 -m "Release libnss-docker-ng 1.2.1-1"
```

### 3. Push the tag

```sh
git push origin debian/1.2.1-1
```

Pushing the tag triggers the release workflow.  Monitor progress in the
**Actions** tab of the repository.  The GitHub Release is created only after
all checks pass.

---

## Packaging-only revision

To release a packaging fix for an existing upstream version:

1. Update `debian/changelog` with a new entry for `1.2.1-2`.
2. Commit and push to `main`; confirm CI passes.
3. Tag and push:

```sh
git tag debian/1.2.1-2
git push origin debian/1.2.1-2
```

`Cargo.toml` is **not** changed for a packaging-only revision; the workflow
validates that the upstream portion of `1.2.1-2` (i.e. `1.2.1`) still matches
`Cargo.toml`.

---

## What the release workflow validates

Before publishing, the workflow runs:

| Check | What it verifies |
|-------|-----------------|
| `ci/check-release-version.sh` | Tag form, tag↔changelog match, changelog↔Cargo.toml upstream version match |
| CI workflow (reused) | Trixie build, lintian, install/removal lifecycle, Docker NSS smoke test |
| Package re-validation | `ci/check-package.sh` runs again on the artifacts being published |

---

## Release artifacts

The GitHub Release includes:

| File | Description |
|------|-------------|
| `libnss-docker-ng_<ver>_<arch>.deb` | Installable Debian package |
| `*.buildinfo` | Reproducibility record: exact build environment and file checksums |
| `*.changes` | Package upload/metadata summary (source+binary metadata) |
| `SHA256SUMS` | SHA-256 checksums for all artifacts |

**Why these artifacts?**  
`dpkg-buildpackage -b` (binary-only build) produces the `.deb`, `.buildinfo`,
and `.changes` files as its standard outputs.  No `.dsc` or `.orig.tar.gz` is
generated for a binary-only build.  `SHA256SUMS` is generated by the release
workflow to allow independent verification of every downloadable file.

---

## Verifying downloaded artifacts

```sh
# Download the release assets, then:
sha256sum --check --ignore-missing SHA256SUMS
```

A successful check prints `OK` for each verified file.

---

## Installing a released `.deb`

```sh
# Verify checksums first (recommended):
sha256sum --check --ignore-missing SHA256SUMS

# Install:
sudo apt install ./libnss-docker-ng_1.2.1-1_amd64.deb
```

`apt install ./` resolves dependencies automatically.  Use the exact filename
from the release page, substituting the correct version and architecture.

---

## Security properties

- The repository state at the tag **completely determines** the package source.
  The workflow does not fetch upstream source, re-download crates, or modify
  the source tree.
- `vendor.tar.gz` committed to the repository is used as-is; all Cargo builds
  run `--offline`.
- Checksums cover every downloadable artifact.
- The release workflow cannot create or move tags, merge branches, or publish
  to an APT repository.
- `GITHUB_TOKEN` permissions are scoped to `contents: write` (GitHub Release
  creation only).
